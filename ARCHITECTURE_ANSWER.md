# Что изменить, если тарифы хранить в БД и редактировать через админку

## Вынесение тарифов в отдельный слой данных

Сейчас все коэффициенты (`RATE_PER_KM_TON = 8`, `URGENT_SURCHARGE_RATE = 0.20`, проценты по типам груза) захардкожены как константы в `DeliveryService` и enum `CargoType`. Чтобы тарифы стали динамическими, нужно ввести сущность `Tariff` (JPA `@Entity`) с полями: `ratePerKmTon`, `urgentSurchargeRate`, плюс справочник `CargoTypeTariff` с полями `cargoType` и `surchargeRate`. `DeliveryService` перестанет обращаться к константам напрямую — вместо этого через `TariffRepository` (Spring Data JPA) он будет запрашивать актуальные значения из БД перед каждым расчётом. Enum `CargoType` останется для валидации входящих запросов, но его коэффициенты будут загружаться из таблицы, а не из поля enum. Для производительности стоит добавить кэширование (`@Cacheable`) с инвалидацией при обновлении тарифа.

## Админский CRUD и разделение API

Появляется второй контроллер — `AdminTariffController` с эндпоинтами `GET/PUT /api/admin/tariffs` и `CRUD /api/admin/cargo-type-tariffs`. Этот контроллер нужно закрыть Spring Security (роль `ADMIN`), тогда как публичный `/api/delivery/calculate` остаётся открытым. При обновлении тарифа через админку контроллер вызывает `TariffService.update(...)`, который сохраняет новые значения в БД и сбрасывает кэш (`@CacheEvict`). Желательно также добавить аудит-лог (кто, когда и какое значение изменил) — простейший вариант через Hibernate Envers или отдельную таблицу `tariff_audit`. Liquibase/Flyway-миграции зафиксируют начальные значения тарифов, чтобы приложение не стартовало с пустыми данными.

## Влияние на тесты

Юнит-тесты `DeliveryService` потребуют мока `TariffRepository` (Mockito), чтобы по-прежнему обходиться без Spring-контекста. Дополнительно появятся интеграционные тесты админского API (`@SpringBootTest` + Testcontainers с PostgreSQL), проверяющие CRUD-операции, права доступа и корректную инвалидацию кэша после изменения тарифа.
